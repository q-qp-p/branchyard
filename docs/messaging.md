# Messaging: one layer for harness-to-harness communication

Written 6 November 2026. A design for the layer every message between harnesses goes through, and the first slice of it, built in this change. Status, 6 November 2026: **design, with a first slice built.** The built part is hermetic (the fake ACP agent, in-process stores, no model): the `messaging` module (`crates/branchyard/src/messaging/`) with its envelope, addresses, kind registry, pipeline and the store columns that carry a kind's payload, trace and idempotency key on SQLite and PostgreSQL; `ask`/`answer`, `report`, `escalate` and the frozen `handoff` re-expressed through the pipeline with their tools, commands, routes and JSON unchanged; and one new capability, a sibling-to-sibling `message` of a registered kind, delivered at the recipient's next turn, on every surface (`by message`, the MCP `message` tool, `branchyard.message`, `Delegate::message`, `POST …/branches/{b}/message`, `Repo::message` in Rust and Python). `ask` takes an idempotency key (`a_keyed_ask_returns_the_first_question_and_refuses_other_text`). Kinds can be declared in `branchyard.toml` (`[[messaging.kinds]]`, test `configured_kinds_are_registered_and_a_bad_one_names_itself` in `peers.rs`, `by_kinds_lists_built_in_and_configured_message_kinds` in `cli.rs`). Ordinary messages are stored with their log entries in one transaction (step 4 of the migration; store conformance case `message_logs`, SQLite here, PostgreSQL in CI only). Since then, peer messages carry a deadline that drops them at the recipient's turn start and are capped at 32 pending per recipient (tests `a_message_past_its_deadline_is_dropped_with_a_warning_on_the_recipients_log` and `a_recipient_with_too_many_pending_peer_messages_refuses_another` in `crates/branchyard/tests/peers.rs`, `an_expired_message_is_acknowledged_but_not_given_to_the_turn` in `inbox.rs`; hermetic, with the deadline waited out by `wait::until`). Tests: `cargo test -p branchyard --test peers --test messaging --test handoffs`, the store conformance suite's `messages` case (SQLite here; PostgreSQL when `BY_TEST_POSTGRES_URL` names a database, which this machine had none of), and the parity tests of `branchyard`, `branchyard-mcp`, `branchyard-cli`, `branchyard-client` and `branchyard-server`. Not done: everything under [Designed, not built](#designed-not-built); no real harness has sent a peer message; the PostgreSQL side ran only its schema upgrade and conformance code paths through the SQLite-mirrored tests, not a live database; the atomic message write mirrors the SQLite one and compiles with `--features postgres`, and its conformance case has not run against PostgreSQL.

## Why

Today each way one harness talks to another is its own code path with its own rules: `ask`, `report`, `escalate` and `answer` share `inbox.rs`; a frozen `handoff` is a second path with its own transaction, dedupe key and fence; the shared brief is a third (entries on the parent's log, steered to running children); a `blocked` or `failure` `report_status` is an escalation the engine sends; a plan approval and a tool approval are escalations the engine renders; a wake is a prompt the engine writes. Each has an authority check, a delivery rule, a size limit and a rendering, written where it was needed. Adding a kind of message means another path. This page makes it one layer: a message is an envelope of a registered kind, and every kind goes through the same stages, so a new one is a registration, not a feature.

## What flows today

Read `docs/delegation.md` for the behaviour; this is the inventory the design has to keep.

Transports: every surface reaches `dispatch` in `delegation.rs` (the MCP server and `by` through the broker's Unix socket, with the turn's token; the Python module through `by --json`; the server through `as_person` on a `Delegate`; a sandboxed harness through the turn's HTTP endpoint), and `inbox::send` or `handoff::relay` does the work.

Duplication and inconsistencies the layer removes or names:

- Two authority checks (`inbox::authorize`, `handoff::check_actor`) and a third rule for who may send an `answer` from `@person`, each spelled in its own place.
- Two idempotency rules: a handoff's hash key, nothing for an ordinary message (a retried `by ask` asks twice).
- Two delivery rules (steer-or-next-turn; next-turn-only) chosen by the kind's code, not declared by the kind.
- Size limits set per feature (none for a question's text, 16 KiB for a handoff note, 64 KiB for a result), and one renderer bound (20 messages, 8,000 characters) that knows nothing about a payload.
- Two atomicity rules for the same event (removed by step 4 of the migration): a handoff's commit appended `Activity::Message` to both logs inside its transaction, while an ordinary message's events were appended after its row, best effort, so a crash between the two left a message no log names.
- The store refuses `next_turn` without a handoff, so no ordinary message could ask to wait for the next turn.
- The `Message` JSON has no place for a payload, a trace or a deadline; a result rides as a separate `Activity::Result`, a handoff as a nested object.
- `report_status`'s escalation, a plan's and an approval's are rendered text, so a parent cannot tell them apart by kind.

## Model

**Addresses.** `messaging::Address` is where a message goes: `Branch(name)` or `Person` (`@person`, which no branch can be named). Designed: `Seat(rig, seat)` (resolved to the branch filling the seat when the message is sent), `Team(parent)` (every live child of a branch; a broadcast), and `External(url)` (a service endpoint of another server, found through the service registry). An address parses from and prints as text (`a`, `@person`), so every surface takes a string.

**The envelope.** `messaging::Envelope` is one message in flight: `kind` (a registered name), `schema_version`, `from`, `to`, `correlation` (the message it replies to), `text` (the one human line every surface shows), `payload` (a JSON value the kind's schema checks), `trace` (a W3C `traceparent`, carried as the sender's turn has it in `TRACEPARENT`; the observability work sets it on a server's turns), `deadline_ms` (after which the message is not delivered), `idempotency_key` and `delivery`. Once stored it is a `Message`: the fields every reader knows (`id`, `from`, `to`, `kind`, `text`, `in_reply_to`, `at_ms`, `delivered`, `handoff`, `next_turn`), plus `meta`, present only when the message carries more than those: the registered `kind` when it is not the legacy one, the `schema_version`, the `payload`, the `trace` and the `deadline_ms`. A message of a legacy kind with no payload and no trace serializes exactly as before, which is what keeps every existing surface byte-identical.

**Kinds and classes.** A *class* says who may send to whom and how it is delivered; a *kind* says what the payload looks like. The classes are the stored `kind` column: `question`, `report`, `escalation`, `answer`, and now `peer` (a message between siblings, children of one parent). A frozen handoff is the `answer` class with `handoff` and next-turn delivery. The registry (`messaging::Registry`) holds `KindSpec`s: the built-in `question`, `report`, `escalation`, `answer`, `handoff` and `note` (class `peer`, any payload), and custom kinds registered by the embedding program (`Yard::register_kind`) with a JSON Schema in the subset `result contracts` use (`type`, `properties`, `required`, `enum`, `pattern`, bounds, `anyOf`/`oneOf`; `$ref`, `allOf`, `not`, `format` refused by name when registered). A kind's name is `[a-z0-9._-]`, not a built-in's. Kinds are also declared in `branchyard.toml` as `[[messaging.kinds]]` (`name`, `schema_version`, `description`, and an inline `schema` table; an inline table rather than a path, so the file that names a kind is the file that defines it and `by config validate` needs nothing else), registered by `Yard::configure` when a yard is opened with `Yard::open_configured`, so `by` outside a harness and a server's workers share them; a configured kind is always class `peer`. The same refusals as `Yard::register_kind` apply (a built-in name, a name taken, `$ref`/`allOf`/`not`/`format`), as a config error naming the kind that registers none of the file's kinds; configuring a yard twice with the same file is not a duplicate. `by kinds [--json]` lists the built-in and configured kinds (name, class, schema version, schema, description) from the configuration on this machine; it is a top-level command because `by message TO TEXT` takes a branch name first, and there is no MCP tool for it (see below).

**Delivery classes.** `Delivery::Steer` is today's default: into the recipient's running turn through the `DeliveryHook`, else prepended to its next turn's prompt. `Delivery::NextTurn` never steers (a frozen handoff, a peer message, whose recipient is doing its own work and reads mail when it next starts). Designed: `Request { timeout }` (today's `ask --wait`, generalized to any kind that declares a reply kind, with the timeout stored so a stalled waiter is not mistaken for a stalled turn, as `set_awaiting` does now), `Broadcast` (to a `Team` address: one row per member, one event on the sender), and `Interrupt` (a steer that also asks the harness to stop its current step; no driver offers this yet).

## Semantics

- **At-least-once from the sender, exactly-once into a turn.** Sending is durable before it returns; a send whose caller lost the connection may be repeated, and an `idempotency_key` makes the repeat return the first message instead of a second one. Delivery is exactly once: acknowledging (marking delivered) is the same store write as handing the message to the turn (`begin_submit`'s journaled `submit` step, or the settled steer), so a crash never delivers twice or drops one. This is unchanged.
- **Ordering per conversation.** Messages are ordered by store id, which counts from 1 across the repository and is assigned in the store's write transaction, so an inbox and a turn's `<branchyard-inbox>` block read oldest first. Two sends from one sender are ordered as they committed; across senders, as the store serialized them. A reply carries `in_reply_to`, which is the conversation key.
- **Idempotency keys.** A key is scoped to the sender (`from/key` in the `idempotency_key` column, unique per repository), so two branches using `step-1` do not collide. A repeat with the same key returns the stored message, delivered or not; the same key from the same sender with a different recipient or text is refused rather than silently answered with the first. A handoff keeps its own hash key: the key *is* the content, since the same frozen result relayed twice is one handoff. `ask` takes the same key on every surface (`by ask --key`, the MCP `ask` tool's `key`, `branchyard.ask(key=)`, `Delegate::ask`, the `key` of `POST …/ask`, `Repo::ask`/`Repo.ask`), with the same rules, and a repeat with `--wait` waits for the first question's answer. `report`, `escalate` and `answer` do not take one, by decision: a repeated `report` or `escalate` is a harmless duplicate line for the parent, an `answer` is already tied to the one question it replies to, and every parameter on a leaf's tool list costs the model-surface budget; a retried `ask` is the case that does harm (it asks twice and starts a second wait).
- **Persistence and replay.** Every message is a `messages` row and an `Activity::Message` on the sender's and recipient's logs: every message's row and its `Activity::Message` entries on the sender's and the recipient's logs (the person keeps none; a branch the store no longer has gets none) are one transaction, a frozen handoff's in its commit and an ordinary message's in `Backend::send_message`, on SQLite and on PostgreSQL. A failure writing either leaves neither, so no message exists that no log names. `persist` wakes waiting readers; `observe` only tells the yard's observer of the events, and tells it nothing for a repeat. The journaled `submit` step holds the combined prompt and the ids it carried, so recovery's replay guarantee covers messages.
- **Back-pressure and size.** A turn is given at most 20 pending messages or about 8,000 characters; the rest wait, with a note. A peer message's `text` is at most 16 KiB and its `payload` 64 KiB, the limits a brief entry and a result already have; a legacy kind keeps its limits so nothing that worked is refused. A recipient with 32 undelivered `peer` messages (`messaging::PEER_PENDING_MAX`, counted over every sender, a message past its deadline not counted) refuses another in `authorize` with `denied`, naming the count and the limit (`b already has 32 undelivered peer messages (the limit is 32); a can send more after b's next turn starts`), so one chatty sibling cannot fill the inbox; a repeat under a key already stored is not refused. A message with a `deadline_ms` that is still pending when the recipient's next turn starts after it is not given to the turn: the same transaction that journals the turn's `submit` marks it delivered (so it is never given late), the prompt leaves it out, and an `Activity::Warning` on the recipient's log names it (`message #12 from a expired: its deadline … passed before turn 3 started, so it was not delivered`), so it is visible in `by log` and never silently lost. A deadline already past when the message is sent is refused. The cap is a constant, not configuration; the expiry is checked at the turn boundary only, so `by inbox` still lists an expired message as undelivered until the recipient's next turn starts.
- **Policy in one place.** Authority (the delegation tree, `escalates_to`, the person's reply-only rule, a handoff's common ancestor, siblings for `peer`), capability (`Capability::Message` for every delegated branch, `Delegate` for `answer` and `handoff`), the envelope's budgets (a message spends nothing and reserves nothing, so none apply, but the stage is where a per-kind quota would go) and ownership (not relevant to a message) are the `authorize` stage. A new kind picks a class and inherits its rule; a kind that needs its own rule registers one as a stage.

## Extensibility

- **Custom kinds.** `Yard::register_kind(KindSpec { name, class, schema, version, delivery })`. The schema is validated when registered (unsupported keywords refused by name) and every payload is validated at the boundary, before anything is stored, with the path and the rule (`payload.step: expected integer, got string`). A kind's `version` is stored with each message; a reader that knows only an older version still reads the row, since `meta` is additive JSON.
- **Middleware.** `messaging::Stage` is one step of the pipeline, `fn apply(&self, yard, cx: &mut Context) -> Result<(), Error>`; `Pipeline::standard()` is `authorize → validate → persist → observe → deliver` (observe sits after persist because the event it records names the store's id, and nothing may say a message exists before it is durable). `Pipeline::then(stage)` appends a stage, `Pipeline::before(name, stage)` inserts one; the built-in stages are named so a redaction stage can sit before `persist` and a rate limit before `authorize`. Designed: a `redact` stage keyed on the kind (strip a payload's named fields before they are stored), a `rate_limit` stage reading the recipient's pending count, and an `observe` stage that opens a span per message from `trace` when the telemetry crate is linked (this change carries the `traceparent`; it does not create spans, which the observability work owns).
- **Transports.** The pipeline is in-process; a transport is how an envelope reaches it: the broker's socket (a harness's `by`, Python and MCP), the server's HTTP routes (`as_person`), and `Yard` directly (an embedding program). The store-backed durable transport is the `messages` table on both backends, reached through `Backend::send_message`, `message_by_key`, `inbox`, `inbox_for_turn`, `mark_delivered`. Designed: a `Transport` trait with `enqueue(Envelope)` so a message to an `External` address is posted to another server's `POST …/message` with the same envelope JSON, and the MCP surface generated from the registry (one tool per class, its `kind` argument an enum of the registered names), so a new kind needs no tool written by hand.
- **Routing.** A `Branch` address is looked up in the store; `Person` is a constant. Designed: `Seat` resolves through the rig's seat assignments; `Team` expands to live children; `External` resolves through the service registry (`by services`, `docs/connectors.md`), with the sender's token exchanged for one the other server accepts.

## Surfaces

The model-facing text is capped (`tools/check_model_surface.py`), and the MCP `tools/list` a leaf sees is capped at 5,800 bytes, so the layer favours few, generic operations with a `kind` over one tool per kind. This change adds one operation, `message` (`to`, `text`, `kind`, `payload`, `key`), under `Capability::Message`, so every delegated branch, a leaf included, has it, and keeps every existing tool as it is: `ask`, `report`, `escalate`, `answer`, `inbox` and `handoff` are the specific verbs a model uses well (a test in `branchyard-mcp` checks that `ask`'s description says what happens, because models read it before choosing), and each is now a thin wrapper that builds an envelope of its class. The trade: a generic `message` with a `kind` argument asks the model to know the registered kinds, which it can list with `by kinds` (a shell command; no MCP tool lists them, because the leaf's tool list and the model-surface text are at their caps, and the MCP `message` description does not name configured kinds for the same reason); the specific verbs carry their meaning in their name. The design keeps both: specific tools for the built-in classes, one generic tool for registered kinds, and (designed) an enum in the tool's schema built from the registry.

A new kind registered by the embedding program needs no new row in `operations.rs`: it is a value of `message`'s `kind`. A new *class* (a new authority rule) is a row, since it is a new operation on every surface, and the parity tests then name each surface still missing it.

How each surface wraps the core, for the slice: `by message TO TEXT [--kind K] [--payload JSON] [--key KEY] [--deadline DURATION] [--as BRANCH] [--json]` calls `Delegate::message`; the MCP `message` tool is dispatched to the same `Local::message`; `branchyard.message(to, text, kind=None, payload=None, key=None, deadline=None)` runs `by message --json`; `POST /v1/repos/{repo}/branches/{b}/message` (`run` scope) acts as `b` through `as_person`, and `Repo::message` in Rust and Python post it. The deadline is a duration from now on the CLI (`10m`; a bare number is seconds) and in Python (`deadline`, seconds), and the moment itself, `deadline_ms` in milliseconds since the epoch, in the HTTP body, `MessageRequest` and the Rust `Delegate::message`. The MCP `message` tool does not take it: a leaf's tool list is capped (`tools/model_surface_budget.json`), the tool is already near that cap, and a model that wants a deadline can run `by message --deadline`. All print or return the stored `Message`.

## Comparison

- **A2A (Agent2Agent).** Agents publish an agent card, and clients send tasks whose messages carry typed `parts` (text, file, data) and whose state machine (`submitted`, `working`, `input-required`, `completed`) is the protocol's. Branchyard takes the typed part (a `payload` beside the `text`, validated by schema) and the correlation of a reply to its request. It rejects the task state machine as the unit of messaging: a Branchyard branch already has a durable status from its turns, and a message must not be a second place where "done" is recorded. It also rejects discovery by card for now: who may be addressed follows the delegation tree, not a directory.
- **MCP.** A tool call is a request/response with a JSON Schema per tool, and the server's `tools/list` is the contract. Branchyard already serves its operations as MCP tools and keeps that: the registry is to kinds what `tools/list` is to tools (a schema per name, validated at the boundary), and the design generates the kind enum into the tool's schema from the registry rather than one tool per kind, because the list a leaf sees is capped. MCP has no durable inbox or delivery semantics, which is why a tool call alone cannot be the transport between two harnesses that run at different times.
- **ACP.** Sessions carry prompts and notifications between a client and an agent, with `_session/steering` as an extension for mid-turn input. Branchyard's `Steer` delivery class is exactly that boundary, recorded per driver as `boundary`; the design keeps delivery classes separate from transport, since the same message may be steered into one harness and prepended to another's next prompt.
- **Actor and mailbox systems** (Erlang, Akka, Warp's `parent_bridge`). One mailbox per actor, at-least-once sends, ordering per sender pair, supervision trees for authority. Branchyard takes the mailbox (a durable inbox per branch), the per-pair ordering, and the tree as the authority model (a supervisor talks to its children). It rejects unbounded mailboxes (the render bound, the designed pending cap) and location transparency across servers until the service registry gives an address a token to go with it.

## Migration

Each step keeps every surface's output and refusals as they are; the tests that already exist are the check.

1. **Done in this change.** `inbox::send` builds an envelope of its class and runs the standard pipeline; `handoff::relay` prepares its frozen commit and runs the pipeline with the handoff class (authorize re-checks the common ancestor, validate runs `HandoffCommit::validate`, persist commits the transaction, which appends the events itself, so observe and deliver do nothing more). `report_status`'s escalation and `report`'s result recording call `inbox::send` as before, so they ride the same path. The store gains `meta` and `idempotency_key`, additive columns that an older binary ignores.
2. **Keys.** Done for `ask` only (one `Param` row; the pipeline already honoured it); not for `report`, `escalate` and `answer`, as decided under Semantics. No behaviour change for a call without one.
3. **Engine messages as kinds.** Register `status` (the `report_status` escalation, payload the `StatusReport`), `plan` (a plan awaiting approval) and `approval` (a tool or connector ask) as kinds of class `escalation`, so a parent's inbox can tell them apart by `meta.kind` while their rendered `text` stays what it is.
4. **One atomicity rule.** Done: `Backend::send_message` appends an ordinary message's `Activity::Message` events in the transaction that inserts its row, as the handoff commit does, so no crash leaves a message that no log names; `observe` only passes the event to the observer. The signature did not change: the backend derives the events from the stored message, and skips an endpoint that is the person or no longer a stored branch, which the old best-effort recorder also did. The store conformance case `message_logs` injects a failure at the recipient's log write (a trigger on the events table) and shows the row, the sender's entry and the idempotency key are all rolled back, and that the retried send logs once on each side; it runs on SQLite here and, with a PL/pgSQL trigger, on PostgreSQL in CI's postgres jobs.
5. **Brief as a kind.** A brief entry becomes a `peer`-less class `brief` from the parent to its live children with `Delivery::Steer`, stored once with a `Team` address and rendered under "The shared brief" as now; the parent's `Activity::Brief` stays.
6. **The wake.** The wake prompt becomes a message of class `wake` from the engine, next-turn delivery, so a parent's inbox shows why it was woken and the prompt is rendered from it.
7. **Generated surface.** Build the MCP `message` tool's `kind` enum and a `kinds` read from the registry (the read is `by kinds` now); then a new kind reaches models with no text edited by hand.

## Decisions

- **Peer messages reach siblings only.** The children of one delegated parent may message each other; a cousin (a branch sharing a grandparent but not a parent), an uncle, the parent, a grandparent, `@person` and a branch in another tree are refused by name (`g1 may only message its siblings, the other children of c1, not g2`), and a root or a fork, which has no parent that delegated it, has no siblings. The reason is that the rule is easy to widen later and hard to narrow: a rule that let cousins talk would have branches in different subtrees depend on each other's inboxes and mailboxes, with no single parent responsible for the exchange, and once a harness or a rig relies on that, removing it breaks work that was running. Siblings share a parent that can see, steer and stop all of them, so the conversation always has a supervisor. Widening (a `Seat` or `Team` address, or an `escalates_to`-style allowance for named ancestors) is a change to `inbox::siblings` and its registered class, not to the pipeline. `a_cousin_is_refused_while_siblings_at_every_depth_are_not` in `peers.rs` holds the rule at depth two.
- **A message keeps the sender's trace.** A message sent under a turn that has a `TRACEPARENT` stores it in `meta.trace` (and nothing else in `meta` for a legacy kind), and both event logs carry the same message. Without one, a legacy message has no `meta` and serializes byte for byte as it did before the layer (`an_ask_under_a_traceparent_carries_it_and_without_one_has_no_meta`). The trace is carried, not turned into spans; see [observability](observability.md#propagation).

## Designed, not built

A `Seat`, `Team` or `External` address; `Request`, `Broadcast` and `Interrupt` delivery; kinds listed to a model through the MCP surface; a redaction or rate-limit stage; spans opened from a message's `trace`; a transport to another server; the generated `kind` enum; steps 3, 5, 6 and 7 of the migration.
